# 5.2 Spark 4.x 流处理主线

在 Spark 4.x 中，本章的推荐学习顺序与工程主线如下：

（1）先掌握处理语义、时间语义和状态管理，这是所有流处理系统的共同基础。

（2）新项目优先使用 Structured Streaming（`readStream` / `writeStream`），以 DataFrame/Dataset 作为统一 API。

（3）将 DStream 视为历史 API 与迁移材料，只在维护存量系统、理解微批演进或阅读旧代码时重点关注。

（4）优先选择 Kafka 等可重放消息系统作为输入源，并配置 checkpoint、水位线和幂等/事务性输出。

为了避免读者在“现代推荐做法”和“历史 API 资料”之间来回切换，本章先明确主线，再保留必要的历史背景。

Structured Streaming 是 Spark 4.x 的默认流处理方案，原因主要有三点：

- 与 Spark SQL、DataFrame、Dataset 统一，批处理与流处理的代码模型更一致。
- 原生支持事件时间、水位线、窗口聚合与状态管理，更适合生产系统。
- 更容易与 Kafka、湖仓、批处理任务和监控体系集成。

DStream 仍有学习价值，但它在本书中的角色应当是“帮助理解微批原理”和“服务于旧系统迁移”，而不是新项目模板。阅读本章时，更建议按下面顺序推进：

1. 先读 5.4 和 5.5，理解处理语义与时间语义。
2. 再重点阅读 5.8 和 5.9，把 Structured Streaming 作为工程落地路径。
3. 最后回看 5.6 和 5.7，把 DStream 作为历史模型和迁移资料来理解。

从数据形态上看，批处理面对的是有界数据集，流处理面对的是持续到达的无界事件流。系统必须在有限资源下持续接收、计算并输出结果，这也是后面需要讨论处理语义、时间语义以及 API 设计差异的根本原因。
