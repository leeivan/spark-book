# 10.3 构建应用

&emsp;&emsp;本节讨论的重点，不是“如何把示例敲出来”，而是“如何把一个 Spark 程序整理成可构建、可打包、可交付的项目”。先看一个最小的 Scala 应用，再围绕它说明依赖管理、项目结构和打包方式。

```scala
/* SimpleApp.scala */

import org.apache.spark.sql.SparkSession

object SimpleApp {
  def main(args: Array[String]): Unit = {
    val logFile = "YOUR_SPARK_HOME/README.md" // Should be some file on your system

    val spark = SparkSession.builder
      .appName("Simple Application")
      .getOrCreate()

    val logData = spark.read.textFile(logFile).cache()
    val numAs = logData.filter(line => line.contains("a")).count()
    val numBs = logData.filter(line => line.contains("b")).count()

    println(s"Lines with a: $numAs, Lines with b: $numBs")
    spark.stop()
  }
}
```

  - 注意

&emsp;&emsp;Scala应用程序应该定义一个main()方法，而不是扩展scala.App，scala.App子类可能无法正常工作。

&emsp;&emsp;这个程序只做一件很小的事情: 统计 README 中包含 `a` 和 `b` 的行数。注意，需要把 `YOUR_SPARK_HOME` 替换成自己的 Spark 安装路径。和前几章直接在交互环境里运行示例不同，独立应用必须自己初始化 SparkSession，并把应用名、依赖和入口类一起整理进项目结构中，后面才能顺利打包和提交。

&emsp;&emsp;由于应用依赖 Spark API，还需要配套一个 `build.sbt` 文件来声明版本、Scala 版本和依赖项。下面是最小可工作的配置：
```scala
name := "Simple Project"
version := "1.0"
scalaVersion := "2.13.16"
libraryDependencies += "org.apache.spark" %% "spark-sql" % "4.1.1"
```

&emsp;&emsp;按照约定把 `build.sbt` 和源码放进标准目录结构后，就可以编译出包含应用代码的 jar，再交给 `spark-submit` 运行。

&emsp;&emsp;SBT 是 Scala 生态里最常见的构建工具之一。如果你熟悉 Maven，可以先把它理解为“更贴近 Scala 项目工作方式”的同类工具：同样负责依赖管理、编译、测试和打包，只是 DSL 和项目组织方式更偏 Scala。对 Spark/Scala 项目来说，它最有价值的地方并不是“功能点更多”，而是三件事：能稳定管理 Spark 与 Scala 版本的匹配关系，能自然处理混合的 Java/Scala 源码布局，也能把从开发到提交所需的 jar 产物持续整理出来。

&emsp;&emsp;从今天的实践来看，新项目通常直接使用 SBT 1.x 系列，早期 0.7/0.10 时代更多属于历史背景。无论内部具体通过 Ivy 还是 Coursier 解析依赖，对读者来说最重要的是：构建工具要能稳定管理 Spark 版本、Scala 版本、第三方依赖，以及最终的打包产物。如果你编写的是纯 Scala 的 Spark 应用，或者仓库里同时包含 Java 与 Scala 代码，那么 SBT 往往是最顺手的选择。

### 10.3.1 sbt

#### 10.3.1.1 项目结构

&emsp;&emsp;如果使用现代的 SBT 1.x 版本，可以通过 `sbt new` 快速初始化一个最小项目，在终端中执行下面的命令即可：

```bash
$ sbt new sbt/scala-seed.g8
....
Minimum Scala build.
name [My Something Project]: hello
Template applied in ./hello
```

&emsp;&emsp;当提示输入项目名称时，可以输入 `hello`。这会在名为 `hello` 的目录下生成一个最小项目。进入该目录后，启动 sbt 并在 sbt shell 中执行 `run`，就能验证构建环境是否正常：

```bash
$ cd hello
$ sbt
...
> run
...
[info] Compiling 1 Scala source to
/xxx/hello/target/scala-2.12/classes...
[info] Running example.Hello
Hello
```

&emsp;&emsp;要离开sbt shell，请键入exit或使用Ctrl + D（Unix）或Ctrl + Z（Windows）。
```bash
> exit
```

&emsp;&emsp;在 sbt 的术语中，基础目录就是包含项目定义的根目录。如果项目根下有 `hello/build.sbt`，那么 `hello` 就是该项目的基础目录。和 Maven 类似，SBT 也遵循一套约定优于配置的标准目录结构。一个最常见的项目布局如下：
```text
build.sbt
lib/
project/
src/
  main/
    resources/
      <files to include in main jar here>
    scala/
      <main Scala sources>
    java/
      <main Java sources>
  test/
    resources/
      <files to include in test jar here>
    scala/
      <test Scala sources>
    java/
      <test Java sources>
```

&emsp;&emsp;其中包含以下重要路径和文件：

  - build.sbt

&emsp;&emsp;这个文件描述项目的核心属性。最常见的做法，是把构建定义写在项目根目录的 `build.sbt` 中；它本质上是一个基于 Scala DSL 的配置文件，用来声明项目名、版本、Scala 版本和依赖关系。`libraryDependencies` 的写法会在下一节继续说明。
```scala
name := "BuildingSBT"
version := "1.0"
scalaVersion := "2.13.16"
libraryDependencies += "org.apache.spark" %% "spark-core" % "4.1.1"
libraryDependencies += "org.apache.spark" %% "spark-sql" % "4.1.1"
libraryDependencies += "org.apache.commons" % "commons-csv" % "1.2"
```

  - lib/

&emsp;&emsp;此目录包含在本地下载的任何非托管库依赖项。

  - project

&emsp;&emsp;已经在项目的基础目录中看到了 `build.sbt`。其他 sbt 相关文件通常位于 `project` 子目录中；这里既可以放 `.scala` 文件来扩展构建逻辑，也可以放 `.sbt` 文件来声明插件。`build.properties` 的职责，是锁定当前项目使用的 SBT 版本，这样不同项目即使共用同一台开发机器，也能各自保持兼容的构建环境。

```bash
# SBT Properties File: controls version of sbt tool
sbt.version=1.10.0
```

&emsp;&emsp;插件本质上是在现有构建之上增加新的设置、任务或打包能力。对 Spark 项目来说，最常见也最实用的插件通常是 `sbt-assembly`，因为它可以把应用和依赖一起打成装配 jar。典型写法是在 `project/assembly.sbt` 中加入：
```scala
addSbtPlugin("com.eed3si9n" % "sbt-assembly" % "0.14.4")
```

&emsp;&emsp;如果某些插件不在默认仓库中，还可以额外声明解析仓库，例如：
```scala
resolvers += Resolver.sonatypeRepo("public")
```

&emsp;&emsp;实际项目里会不会用到更多插件，取决于团队对代码质量、发布流程和打包方式的要求；但对本章来说，先掌握 `sbt-assembly` 这一类和交付直接相关的插件就够用了。

  - src

&emsp;&emsp;SBT 默认沿用和 Maven 接近的目录约定，所有路径都相对于项目根目录解释。小型示例当然可以把源码直接放在根目录下，但真实项目通常仍会把实现放进 `src/main/scala` 或 `src/main/java`，这样目录职责更清楚，也更方便和测试代码、资源文件一起维护。

  - target

&emsp;&emsp;`target/` 用来存放编译产物、中间文件和最终 jar。通常它属于构建输出目录，不建议把人工维护的文件放进去。

&emsp;&emsp;下面保留一个很小的 Spark 示例，并额外引入 `commons-csv` 作为第三方依赖。这样做不是为了演示某个特定库，而是为了把“受管理依赖”“提交时动态分发依赖”和“装配 jar”这三种常见交付方式串起来看清楚。

```scala
/**
 * A simple Scala application with an external dependency to
 * demonstrate building and submitting as well as creating an
 * assembly jar.
 */
object SBuilding {
  def main(args: Array[String]): Unit = {
    val spark = SparkSession.builder.appName("SBuilding").getOrCreate()

    // Create a simple RDD containing 4 numbers.
    val numbers = Array(1, 2, 3, 4)
    val numbersListRdd = spark.sparkContext.parallelize(numbers)

    // Convert this RDD into CSV (using Java CSV Commons library).
    val printer = new CSVPrinter(Console.out, CSVFormat.DEFAULT)
    val javaArray: Array[java.lang.Integer] =
      numbersListRdd.collect().map(java.lang.Integer.valueOf)

    printer.printRecords(javaArray)
    spark.stop()
  }
}
```

#### 10.3.1.2 编译集成

&emsp;&emsp;在依赖解析层面，SBT 会从 Maven 仓库下载并管理依赖。`build.sbt` 中最常见的写法是 `groupID % artifactID % version` 或 `groupID %% artifactID % version`。下面这组配置同时声明了 Spark Core、Spark SQL 和一个额外的 Commons CSV 依赖：
```scala
libraryDependencies += "org.apache.spark" %% "spark-core" % "4.1.1"
libraryDependencies += "org.apache.spark" %% "spark-sql" % "4.1.1"
libraryDependencies += "org.apache.commons" % "commons-csv" % "1.2"
```

&emsp;&emsp;如果使用 `groupID %% artifactID % version`，SBT 会自动把当前 Scala 版本追加到 artifact 名称中，例如把 `spark-core` 解析成 `spark-core_2.13`。这对 Spark 这类跨 Scala 版本发布的库尤其重要。纯 Java 依赖通常仍然使用单个 `%`。如果不知道某个库的 `groupID` 或 `artifactID`，通常可以在项目主页或 Maven Central 上查询。

```bash
cd /root/spark-app/building-sbt
sbt clean
sbt package
# (This command may take a long time on its first run)
```

&emsp;&emsp;`package` 命令会编译 `src/main` 下的源代码，并生成一个只包含项目自身代码的 jar，而不会自动把第三方依赖一起打进去。对于简单示例这已经足够，但一旦应用要部署到真实环境，就需要进一步决定依赖是靠 `--packages`、`--jars` 还是装配 jar 分发。

&emsp;&emsp;实践里可以把这个选择理解成一个简单的交付判断路径：开发阶段先用 `package` 验证项目本身能否稳定编译；如果额外依赖已经发布到 Maven 仓库，而且数量不多，通常优先用 `--packages`，这样提交命令更轻，也方便临时替换版本；如果依赖是团队自建 jar、商业驱动或本地文件，则更适合通过 `--jars` 显式分发；当应用需要交给别的环境长期运行，或者希望把代码与依赖一起固定成一个可复用产物时，再考虑 assembly 这类装配 jar。这样看，打包方式并不是“谁更高级”，而是“谁更适合当前交付边界”。

&emsp;&emsp;如果依赖本身已经发布到 Maven 仓库，一个最省事的做法是在提交时使用 `--packages`。它使用 Maven 坐标语法，而不是 SBT 的 `%/%%` DSL；Spark 运行时自身通常由集群环境提供，所以这里不需要再把 `spark-core`、`spark-sql` 之类的模块重复写进提交参数。对于数量不多、且希望在提交时再解析的附加库，`--packages` 往往是最轻量的选择。

```text
# Run the Scala version.
cd /root/spark-app/building-sbt
$SPARK_HOME/bin/spark-submit \
--class com.pinecone.SBuilding \
--packages org.apache.commons:commons-csv:1.2 \
target/scala-2.13/buildingsbt_2.13-1.0.jar
```

&emsp;&emsp;除了通过受管理依赖让 SBT 自动下载库，也可以手工把 jar 放进本地 `lib/` 目录。不过这种方式更适合作为兼容性补救或离线环境下的备选方案，而不是默认工作流：

&emsp;&emsp;（1）先在 `build.sbt` 中移除对应的受管理依赖，避免同一个库同时出现两套来源。
```scala
libraryDependencies += "org.apache.spark" %% "spark-core" % "4.1.1"
libraryDependencies += "org.apache.spark" %% "spark-sql" % "4.1.1"
//libraryDependencies += "org.apache.commons" % "commons-csv" % "1.2"
```

&emsp;&emsp;（2）再把 Commons CSV 的 jar 放进本地 `lib/` 目录。SBT 会把该目录中的 jar 自动加入编译类路径。
```bash
cd /root/spark-app/building-sbt/lib
wget http://central.maven.org/maven2/org/apache/commons/commons-csv/1.2/commons-csv-1.2.jar
```

&emsp;&emsp;（3）随后照常执行构建命令，最终会得到和前一种方式等价的应用 jar。

&emsp;&emsp;（4）提交时，再通过 `--jars` 显式把这些本地 jar 一并分发到运行环境。这个选项更适合处理没有发布到公共仓库的内部库、临时补丁包，或者已经事先下载好的离线依赖。

```text
# Run the Scala version.
cd /root/spark-app/building-sbt
$SPARK_HOME/bin/spark-submit \
--class com.pinecone.SBuildingSBT \
--jars lib/commons-csv-1.2.jar \
target/scala-2.13/buildingsbt_2.13-1.0.jar
```

&emsp;&emsp;作为最佳实践，不要同时在 `build.sbt` 和 `lib/` 目录里维护同一个依赖的两份来源；一旦版本不一致，排查类冲突会很耗时间。另外，Spark 自身已经会把核心运行时加入类路径，如果再把同版本或不同版本的 Spark 依赖打进应用产物，往往会引发更隐蔽的冲突。

#### 10.3.1.3 创建jar

&emsp;&emsp;当依赖越来越多时，如果仍然把一堆零散 jar 分发到集群上的每个执行器，网络传输和类路径管理都会变得更麻烦。更常见的做法是把应用代码和大部分依赖一起打成一个装配 jar（assembly jar，也常叫 uber jar），这样提交时只需要分发一个主要产物。对于批处理任务、定时作业和需要稳定复现的交付流程，这通常是最省心的方式。使用 `sbt-assembly` 插件可以完成这件事，示例项目里的 `project/assembly.sbt` 就是对应配置：
```scala
addSbtPlugin("com.eed3si9n" % "sbt-assembly" % "0.14.4")
```

&emsp;&emsp;接着把运行环境本来就会提供的 Spark 依赖标记为 `provided`，避免它们被重复打进装配 jar。像 `commons-csv` 这类真正需要随应用一起分发的第三方依赖，则保持普通依赖即可。
```scala
libraryDependencies += "org.apache.spark" %% "spark-core" % "4.1.1" % provided
libraryDependencies += "org.apache.spark" %% "spark-sql" % "4.1.1" % provided
libraryDependencies += "org.apache.commons" % "commons-csv" % "1.2"
```

&emsp;&emsp;接下来，运行 `assembly` 命令，就会生成包含应用代码和第三方依赖的装配 jar。
```bash
cd /root/spark-app/building-sbt
sbt assembly
```

&emsp;&emsp;实际项目里往往还会继续补充 `MergeStrategy` 等配置，用来解决资源文件重复、`META-INF` 冲突或服务发现文件合并等问题。装配完成后，可以先简单检查 jar 中是否已经包含目标依赖：

```bash
cd /root/spark-app/building-sbt
jar tf target/scala-2.13/BuildingSBT-assembly-1.0.jar | grep commons
```

```text
META-INF/LICENSE_commons-csv-1.2.txt
META-INF/NOTICE_commons-csv-1.2.txt
org/apache/commons/csv/Assertions.class
org/apache/commons/csv/CSVFormat.class
org/apache/commons/csv/CSVParser.class
org/apache/commons/csv/CSVPrinter.class
org/apache/commons/csv/CSVRecord.class
```

&emsp;&emsp;现在就可以直接用装配 jar 提交应用了。因为第三方依赖已经打进产物中，所以通常不再需要额外传 `--jars` 或 `--packages`：

```text
# Run the Scala version.
cd /root/spark-app/building-sbt
$SPARK_HOME/bin/spark-submit \
--class com.pinecone.SBuildingSBT \
target/scala-2.13/BuildingSBT-assembly-1.0.jar
```
