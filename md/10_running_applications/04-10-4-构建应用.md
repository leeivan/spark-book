# 10.4 构建应用

本节讨论的重点，不是“如何把示例敲出来”，而是“如何把一个 Spark 程序整理成可构建、可打包、可交付的项目”。先看一个最小的 Scala 应用，再围绕它说明依赖管理、项目结构和打包方式。

/\* SimpleApp.scala \*/

import org.apache.spark.sql.SparkSession

object SimpleApp {

def main(args: Array\[String\]) {

val logFile = "YOUR\_SPARK\_HOME/README.md" // Should be some file on
your system

val spark = SparkSession.builder.appName("Simple
Application").getOrCreate()

val logData = spark.read.textFile(logFile).cache()

val numAs = logData.filter(line =\> line.contains("a")).count()

val numBs = logData.filter(line =\> line.contains("b")).count()

println(s"Lines with a: $numAs, Lines with b: $numBs")

spark.stop()

}

}

代码 10.14
  - 注意

Scala应用程序应该定义一个main()方法，而不是扩展scala.App，scala.App子类可能无法正常工作。

这个程序只做一件很小的事情: 统计 README 中包含 `a` 和 `b` 的行数。注意，需要把 `YOUR_SPARK_HOME` 替换成自己的 Spark 安装路径。和前几章直接在交互环境里运行示例不同，独立应用必须自己初始化 SparkSession，并把应用名、依赖和入口类一起整理进项目结构中，后面才能顺利打包和提交。

由于应用依赖 Spark API，还需要配套一个 `build.sbt` 文件来声明版本、Scala 版本和依赖项。下面是最小可工作的配置：

name := "Simple Project"

version := "1.0"

scalaVersion := "2.13.16"

libraryDependencies += "org.apache.spark" %% "spark-sql" % "4.1.1"

代码 10.15
按照约定把 `build.sbt` 和源码放进标准目录结构后，就可以编译出包含应用代码的 jar，再交给 `spark-submit` 运行。

SBT 是 Scala 生态里最常见的构建工具之一。如果你熟悉 Maven，可以先把它理解为“更贴近 Scala 项目工作方式”的同类工具：同样负责依赖管理、编译、测试和打包，只是 DSL 和项目组织方式更偏 Scala。对于 Spark/Scala 项目，SBT 常见的优势包括：

（1）使用Scala作为DSL来定义build文件

（2）通过触发执行特性支持持续的编译与测试

（3）增量编译

（4）可以混合构建Java和Scala项目

（5）并行的任务执行

（6）可以重用Maven或者ivy的repository进行依赖管理

从今天的实践来看，新项目通常直接使用 SBT 1.x 系列，早期 0.7/0.10 时代更多属于历史背景。无论内部具体通过 Ivy 还是 Coursier 解析依赖，对读者来说最重要的是：构建工具要能稳定管理 Spark 版本、Scala 版本、第三方依赖，以及最终的打包产物。如果你编写的是纯 Scala 的 Spark 应用，或者仓库里同时包含 Java 与 Scala 代码，那么 SBT 往往是最顺手的选择。

### 10.4.1 sbt

#### 10.4.1.1 项目结构

如果使用现代的 SBT 1.x 版本，可以通过 `sbt new` 快速初始化一个最小项目，在终端中执行下面的命令即可：

```bash
$ sbt new sbt/scala-seed.g8
....

name [My Something Project]: hello

```

命令 10.2

在 sbt 的术语中，基础目录就是包含项目定义的根目录。如果项目根下有 `hello/build.sbt`，那么 `hello` 就是该项目的基础目录。和 Maven 类似，SBT 也遵循一套约定优于配置的标准目录结构。一个最常见的项目布局如下：

build.sbt

lib/

project/

src/

main/

resources/

\<files to include in main jar here\>

scala/

\<main Scala sources\>

java/

\<main Java sources\>

test/

resources

\<files to include in test jar here\>

scala/

\<test Scala sources\>

java/

\<test Java sources\>

其中包含以下重要路径和文件：

  - build.sbt

这个文件描述项目的核心属性。最常见的做法，是把构建定义写在项目根目录的 `build.sbt` 中；它本质上是一个基于 Scala DSL 的配置文件，用来声明项目名、版本、Scala 版本和依赖关系。`libraryDependencies` 的写法会在下一节继续说明。

name := "BuildingSBT"

version := "1.0"

scalaVersion := "2.13.16"

libraryDependencies += "org.apache.spark" %% "spark-core" % "4.1.1"

libraryDependencies += "org.apache.spark" %% "spark-sql" % "4.1.1"

libraryDependencies += "org.apache.commons" % "commons-csv" % "1.2"

代码 10.17
  - lib/

此目录包含在本地下载的任何非托管库依赖项。

  - project

已经在项目的基础目录中看到了 `build.sbt`。其他 sbt 相关文件通常位于 `project` 子目录中；这里既可以放 `.scala` 文件来扩展构建逻辑，也可以放 `.sbt` 文件来声明插件。`build.properties` 的职责，是锁定当前项目使用的 SBT 版本，这样不同项目即使共用同一台开发机器，也能各自保持兼容的构建环境。

```bash
# SBT Properties File: controls version of sbt tool
sbt.version=1.10.0
```

代码 10.18
插件本质上是在现有构建之上增加新的设置、任务或打包能力。对 Spark 项目来说，最常见也最实用的插件通常是 `sbt-assembly`，因为它可以把应用和依赖一起打成装配 jar。典型写法是在 `project/assembly.sbt` 中加入：

addSbtPlugin("com.eed3si9n" % "sbt-assembly" % "0.14.4")

代码 10.19
如果某些插件不在默认仓库中，还可以额外声明解析仓库，例如：

resolvers += Resolver.sonatypeRepo("public")

代码 10.20
实际项目里会不会用到更多插件，取决于团队对代码质量、发布流程和打包方式的要求；但对本章来说，先掌握 `sbt-assembly` 这一类和交付直接相关的插件就够用了。

  - src

sbt默认使用与Maven相同的目录结构放置源文件，所有路径都相对于基本目录。在src/中的其他目录将被忽略。另外，所有隐藏的目录都将被忽略。源代码可以放在项目的基本目录中hello/app.scala，这可能适用于小型项目，但对于普通项目，人们倾向于将项目放在src/main/目录中以保持整洁。src/main/java这个目录是SBT希望放Java源代码的地方；src/main/scala这个目录是SBT放Scala源代码的地方。

  - target

此目录是SBT放置编译的类和jar文件的位置。

最后，有两个非常简单的Spark应用程序（在Java和Scala中）用于演示SBT。每个应用程序都依赖于Apache Commons
CSV库，因此可以演示SBT如何处理依赖关系。

/\*\*

\* A simple Scala application with an external dependency to

\* demonstrate building and submitting as well as creating an

\* assembly jar.

\*/

object SBuilding{

def main(args: Array\[String\]) {

val spark = SparkSession.builder.appName("SBuilding").getOrCreate()

// Create a simple RDD containing 4 numbers.

val numbers = Array(1, 2, 3, 4)

val numbersListRdd = spark.sparkContext.parallelize(numbers)

// Convert this RDD into CSV (using Java CSV Commons library).

val printer = new CSVPrinter(Console.out, CSVFormat.DEFAULT)

val javaArray: Array\[java.lang.Integer\] = numbersListRdd.collect() map
java.lang.Integer.valueOf

printer.printRecords(javaArray)

spark.stop()

}

}

代码 10.22
#### 10.4.1.2 编译集成

在依赖解析层面，SBT 会从 Maven 仓库下载并管理依赖。`build.sbt` 中最常见的写法是 `groupID % artifactID % version` 或 `groupID %% artifactID % version`。下面的示例同时声明了 Spark Core、Spark SQL 和一个额外的 Commons CSV 依赖：

libraryDependencies += "org.apache.spark" %% "spark-core" % "4.1.1"

libraryDependencies += "org.apache.spark" %% "spark-sql" % "4.1.1"

libraryDependencies += "org.apache.commons" % "commons-csv" % "1.2"

代码 10.23
如果使用 `groupID %% artifactID % version`，SBT 会自动把当前 Scala 版本追加到 artifact 名称中，例如把 `spark-core` 解析成 `spark-core_2.13`。这对 Spark 这类跨 Scala 版本发布的库尤其重要。纯 Java 依赖通常仍然使用单个 `%`。如果不知道某个库的 `groupID` 或 `artifactID`，通常可以在项目主页或 Maven Central 上查询。

cd /root/spark-app/building-sbt

sbt clean

sbt package

命令 10.3 SBT构建命令

`package` 命令会编译 `src/main` 下的源代码，并生成一个只包含项目自身代码的 jar，而不会自动把第三方依赖一起打进去。对于简单示例这已经足够，但一旦应用要部署到真实环境，就需要进一步决定依赖是靠 `--packages`、`--jars` 还是装配 jar 分发。

现在可以使用熟悉的spark-submit脚本运行这些应用程序。使用--packages参数将Commons
CSV作为运行时依赖关系。记住，spark-submit使用Maven语法，而不是SBT语法（冒号作为分隔符而不是百分号），并且不需要将Spark本身作为依赖关系，因为默认情况下它是隐含的。可以使用逗号分隔列表添加其他Maven
ID。

```text
# Run the Scala version.
cd /root/spark-app/building-sbt
$SPARK_HOME/bin/spark-submit \
--class com.pinecone.SBuilding \
--packages org.apache.commons:commons-csv:1.2 \
target/scala-2.13/buildingsbt_2.13-1.0.jar
```

命令 10.5

除了通过受管理依赖让 SBT 自动下载库，也可以手工把 jar 放进本地 `lib/` 目录。不过这种方式更适合作为兼容性补救或离线环境下的备选方案，而不是默认工作流：

（1）更新build.sbt文件以删除Commons CSV依赖关系。

（3）像前面一样继续执行构建命令，最终会得到与之前方法等价的jar文件。

作为最佳实践，不要同时在 `build.sbt` 和 `lib/` 目录里维护同一个依赖的两份来源；一旦版本不一致，排查类冲突会很耗时间。另外，Spark 自身已经会把核心运行时加入类路径，如果再把同版本或不同版本的 Spark 依赖打进应用产物，往往会引发更隐蔽的冲突。

#### 10.4.1.3 创建jar

当依赖越来越多时，如果仍然把一堆零散 jar 分发到集群上的每个执行器，网络传输和类路径管理都会变得更麻烦。更常见的做法是把应用代码和大部分依赖一起打成一个装配 jar（assembly jar，也常叫 uber jar），这样提交时只需要分发一个主要产物。使用 sbt-assembly 插件可以完成这件事，示例项目里的 `project/assembly.sbt` 就是对应配置：

addSbtPlugin("com.eed3si9n" % "sbt-assembly" % "0.14.4")

代码 10.25
更新build.sbt文件将所提供的Spark依赖关系标记为provided。这防止依赖关系被包含在装配jar中。如果需要，还可以恢复Commons
CSV依赖关系，尽管lib/目录中的本地副本仍将在编译时自动获取。

libraryDependencies += "org.apache.spark" %% "spark-core" % "4.1.1" %
provided

libraryDependencies += "org.apache.spark" %% "spark-sql" % "4.1.1" %
provided

libraryDependencies += "org.apache.commons" % "commons-csv" % "1.2"
