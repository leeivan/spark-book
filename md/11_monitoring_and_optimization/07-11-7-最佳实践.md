# 11.7 最佳实践

### 11.7.1 系统配置

从工程实践看，Spark 配置通常来自三个入口：应用级的 Spark 属性，适合描述当前作业的运行参数；机器级或进程级的环境变量，适合放在 `conf/spark-env.sh` 这类文件里；以及日志配置，用来控制输出级别、落盘位置和排障信号。真正做问题定位时，最重要的不是记住每个入口的名字，而是先分清“这是应用参数、机器参数，还是日志策略”，再去对应位置查找和修改。

#### 11.7.1.1 Spark属性

Spark 属性控制大多数应用级行为，可以直接通过 `SparkConf` 设置，也可以通过 `spark-submit` 和配置文件在运行时注入。对于示例代码，`SparkConf` 最适合放那些“必须和代码一起表达”的设置，例如应用名；而资源规模、部署模式、执行器数量这类更容易随环境变化的参数，通常更适合留给提交阶段决定。下面是一个最小示例：

val conf = new SparkConf()

.setMaster("local\[2\]")

.setAppName("CountingSheep")

val sc = new SparkContext(conf)

代码 11.6
这里使用 `local[2]`，表示本地用两个线程运行。它的价值不在于模拟真实集群，而在于帮助我们更早发现某些只在并发执行下才会暴露的问题。对于时间和容量这类配置，最好始终显式写出单位，避免不同属性对“裸数字”的解释不一致：

25ms (milliseconds)

5s (seconds)

10m or 10min (minutes)

3h (hours)

5d (days)

1y (years)

代码 11.7
指定字节大小的属性应该使用大小单位进行配置。以下格式被接受：

1b (bytes)

1k or 1kb (kibibytes = 1024 bytes)

1m or 1mb (mebibytes = 1024 kibibytes)

1g or 1gb (gibibytes = 1024 mebibytes)

1t or 1tb (tebibytes = 1024 gibibytes)

1p or 1pb (pebibytes = 1024 tebibytes)

代码 11.8

Spark 属性可以粗略分成两类：一类偏部署，例如 `spark.driver.memory`、`spark.executor.instances`，更适合在提交阶段设置；另一类偏运行时行为，例如 `spark.task.maxFailures`，通常放在代码、提交命令或默认配置里都可以。把这两类分开看，能减少“为什么我在代码里改了资源参数却没按预期生效”的困惑。

Spark 应用启动后，通常可以通过 `http://<driver>:4040` 打开 Spark UI。在“Environment”选项卡里，可以看到那些通过 `spark-defaults.conf`、`SparkConf` 或命令行显式传入的属性。排查“某个参数到底有没有生效”时，这里往往是最快的确认入口；没有显示出来的参数，一般就意味着仍在使用默认值。

#### 11.7.1.2 环境变量

某些 Spark 设置更适合通过环境变量提供，这类变量通常写在 Spark 安装目录下的 `conf/spark-env.sh` 中；在 Windows 环境里，对应的是 `conf/spark-env.cmd`。这个文件更适合放机器级、运行时级的配置，例如 Java 路径、对外通告地址或 PySpark 解释器路径，而不是每个应用都可能变化的业务参数。默认安装里通常只有模板文件 `conf/spark-env.sh.template`，需要复制一份再按实际环境填写。下面列出几项最常见的变量：

#### 11.7.1.3 设置日志

日志配置的核心目标，不是把每个 log4j 选项都背下来，而是能完成三件事：调低无关噪声、保留关键异常、把日志送到你能稳定检索的位置。传统 Spark 安装通常通过 `conf/log4j.properties` 或模板文件派生配置：

```bash
# Set everything to be logged to the console
log4j.rootCategory=ERROR, console
log4j.appender.console=org.apache.log4j.ConsoleAppender
log4j.appender.console.target=System.err
log4j.appender.console.layout=org.apache.log4j.PatternLayout
log4j.appender.console.layout.ConversionPattern=%d{yy/MM/dd HH:mm:ss} %p
%c{1}: %m%n
# Set the default spark-shell log level to ERROR. When running the
spark-shell, the
# log level for this class is used to overwrite the root logger's log
level, so that
# the user can have different defaults for the shell and regular Spark
apps.
log4j.logger.org.apache.spark.repl.Main=ERROR
# Settings to quiet third party logs that are too verbose
log4j.logger.org.spark_project.jetty=ERROR
log4j.logger.org.spark_project.jetty.util.component.AbstractLifeCycle=ERROR
log4j.logger.org.apache.spark.repl.SparkIMain$exprTyper=ERROR
log4j.logger.org.apache.spark.repl.SparkILoop$SparkILoopInterpreter=ERROR
log4j.logger.org.apache.parquet=ERROR
log4j.logger.parquet=ERROR
# SPARK-9183: Settings to avoid annoying messages when looking up
nonexistent UDFs in SparkSQL with Hive support
log4j.logger.org.apache.hadoop.hive.metastore.RetryingHMSHandler=FATAL
log4j.logger.org.apache.hadoop.hive.ql.exec.FunctionRegistry=ERROR
```

代码 11.12
把 `log4j.rootCategory=INFO, console` 改成 `WARN`，通常就能显著减少控制台噪声；如果需要更细粒度排查问题，再临时切到 `INFO` 或 `DEBUG`。真正长期有用的做法，是把应用日志和平台日志都汇聚到统一位置，而不是只盯着交互终端输出。根 Logger 的基本写法如下：

log4j.rootLogger = \[level\],appenderName,appenderName2,...

代码 11.13
这里最值得掌握的是三件事：日志级别控制“输出多少”，appender 控制“输出到哪里”，layout 控制“长什么样”。在日常排障里，常用的级别主要是 `DEBUG`、`INFO`、`WARN` 和 `ERROR`。如果把根日志级别设成 `INFO`，那么 `DEBUG` 级别的日志默认就不会输出；而线上环境通常更适合从 `WARN` 或 `ERROR` 起步，避免无关噪声淹没有用信息。

常见的输出目标大致有三类：控制台输出，适合本地调试或短任务；滚动文件输出，适合需要保留节点本地日志的场景；集中式日志采集，适合生产环境统一检索。对应到 log4j 术语里，前两类通常由不同的 appender 实现，而生产系统里更关键的其实不是类名本身，而是“能否稳定写到你后续看得到的地方”。

日志格式通常使用 `PatternLayout` 这类可配置布局来完成。一个实用的最小模式一般会包含时间、级别、线程名、logger 名称和消息内容，例如：

```text
%d{yy/MM/dd HH:mm:ss} %-5p [%t] %c{1}: %m%n
```

代码 11.14

这类模式里，`%d` 表示时间，`%p` 表示日志级别，`%t` 表示线程名，`%c` 表示 logger 名称，`%m` 表示消息正文，`%n` 表示换行。知道这些最常用占位符后，通常就足够阅读和调整大部分 Spark 应用的日志配置了；至于更完整的 appender/layout 选项，按具体运行环境查对应版本文档会更稳。

如果某个作业突然变慢，一个实用的排障顺序是：先到 Spark UI 的 Environment 页面确认最终生效的参数，再去 Jobs 页面定位最慢的作业，然后进入对应的 Stages 页面看时间是否主要耗在 Shuffle、数据倾斜或长尾任务上；如果怀疑资源分配不均，就继续看 Executors 页面确认是否有节点明显更忙或失败重试偏多；如果程序本来依赖缓存，还应再看 Storage 页面判断缓存是否真的命中。这样做的好处是先把“配置有没有生效”和“瓶颈发生在哪一层”分开，再决定是否需要调整并行度、缓存策略、序列化方式或代码本身。

如果应用本身是 Structured Streaming，上面这条路径还应再补一个入口：Structured Streaming 页面。它更适合看输入速率、处理速率、批次持续时间、状态算子指标以及 source / sink 的运行状态。很多“批处理页面看起来没问题，但流任务就是越跑越慢”的问题，真正的线索往往藏在这里，例如状态膨胀、迟到数据过多，或者某个 sink 的写出速度已经跟不上输入节奏。

### 11.7.2 程序调优

进入调优阶段后，还要先分清程序主要走的是哪条执行路径。如果主体是 RDD，很多判断会围绕分区、序列化和算子选择展开；如果主体是 DataFrame / SQL，那么 Adaptive Query Execution（AQE） 这类运行时优化就必须纳入视野。此时不要只盯着提交前的静态 `EXPLAIN`，更可靠的做法是结合 Web UI、运行时统计和最终执行结果，看 Spark 实际采用了什么 Join 策略、是否合并了分区、有没有识别出倾斜，再决定是否需要额外 hint 或手工改写。

#### 11.7.2.5 reduceByKey

假设我们要为每个键收集对应的唯一字符串。一种直接写法，是先把每条记录映射成一个只包含单个元素的集合，再用 `reduceByKey` 把这些集合合并：

++= set2)

#### 11.7.2.6 广播变量

广播变量这个主题，最容易让人混淆的地方，是“Driver 上的普通变量”和“分布式执行时真正共享的数据”并不是一回事。下面这个例子展示了一个典型误区：试图在 `foreach` 里直接修改 Driver 侧变量。

var counter = 0

var rdd = sc.parallelize(data)

// Wrong: Don't do this\!\!

rdd.foreach(x =\> counter += x)

println("Counter value: " + counter)

代码 11.32
上述代码的行为并不可靠。原因在于，Spark 会把任务闭包序列化后发送给各个执行器执行；闭包里引用到的变量，到了执行器侧通常已经变成了拷贝，而不是 Driver 里那份可共享的原始对象。

在集群模式下，`foreach` 里看到的 `counter` 并不是 Driver 端那份共享变量，因此执行器里对它做的修改不会自动回写到 Driver。这个例子最容易帮助读者理解“闭包变量”和“分布式共享状态”不是一回事。

在本地模式下，这段代码有时看起来“似乎能工作”，只是因为执行和 Driver 恰好在同一个 JVM 里，这种现象并不能推广到分布式环境。真正需要跨任务安全汇总数值时，应使用 Accumulator；需要高效分发只读大对象时，应使用 Broadcast 变量。

一般来说，闭包不应该被用来修改全局状态；本地模式里偶尔“看起来没问题”的写法，到集群里往往就会变成隐蔽 bug。另一个代价是传输成本：如果闭包里带着一个很大的数组或映射，它可能会随着任务被重复序列化并发送出去很多次；而 Broadcast 变量只需要按节点分发一次，成本会低得多。

val array: Array\[Int\] = // some huge array

val broadcasted = sc.broadcast(array)

代码 11.33
再看一个更常见的场景：闭包里引用了一个很大的查找数组。

val rdd: RDD\[Int\] = // some RDD

代码 11.34
如果直接在闭包里使用它，这个数组可能会随着任务被重复序列化和分发：

如果改成广播变量，执行器通常只需要按节点接收一次副本：

rdd.map(i =\> broadcasted.value.contains(i))

广播出去的值应当视为只读数据。一旦某个节点开始使用这份副本，就不应该再依赖修改其内容来驱动程序逻辑，否则很容易出现各节点看到的数据不一致。

如果某个小型 RDD 或维表能够放进每个工作节点的内存，就可以把它广播出去，把原本需要 shuffle 的连接改写成 map-side join。这样做的关键收益，是避免让大 RDD 为了连接操作整体重分区。

val smallLookup = sc.broadcast(smallRDD.collect.toMap)

largeRDD.flatMap { case(key, value) =\>

smallLookup.value.get(key).map { otherValue =\>

(key, (value, otherValue))

}

}

如果完整的小 RDD 还放不下，但它的键集合放得下，也可以先广播键集合，在 shuffle 之前过滤掉大 RDD 中必然不会命中的记录。只有当这一步能显著缩小数据量时，这种优化才真正划算。

val keys = sc.broadcast(mediumRDD.map(\_.\_1).collect.toSet)

val reducedRDD = largeRDD.filter{ case(key, value) =\>
keys.value.contains(key) }

reducedRDD.join(mediumRDD)

值得注意的是，这里的效率增益取决于实际filter操作减小多少RDD的尺寸。如果在这里减少的条目不多，可能因为小RDD中的键是大RDD的大部分，那么这种策略就没有什么作用。

#### 11.7.2.7 存储级别

能缓存并不意味着就应该缓存。是否值得缓存，取决于数据会不会被重复访问、重算成本高不高、以及缓存后是否真的放得进可用内存。如果某个数据集只会被读取一次，缓存通常只会增加额外开销。默认的 `cache()` 等价于 `MEMORY_ONLY`；当数据偏大、GC 压力明显或者重算代价高时，`MEMORY_AND_DISK` 或序列化存储级别通常更稳妥。

| 存储级别                                  | 含义                                                                                                                                    |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| MEMORY\_ONLY                          | 以反序列化 Java 对象形式缓存在 JVM 堆中。如果放不下，超出的分区不会被缓存，而是在下次访问时重算。这是默认级别。                                                              |
| MEMORY\_AND\_DISK                     | 先以内存缓存；放不下的分区溢写到磁盘，后续直接从磁盘读取，而不是重算。                                                                      |
| MEMORY\_ONLY\_SER                     | 以序列化形式缓存，每个分区是一段字节数组。相比反序列化对象更省内存，但读取时更耗 CPU，通常适合数据较大或配合更高效序列化器使用。 |
| MEMORY\_AND\_DISK\_SER                | 与 `MEMORY_ONLY_SER` 类似，但超出内存的分区会落盘。                                                                                 |
| DISK\_ONLY                            | 只把分区存到磁盘上。                                                                                                                        |
| MEMORY\_ONLY\_2，MEMORY\_AND\_DISK\_2等 | 与对应级别相同，但会在两个节点上保留副本，以提升容错性。                                                                                                             |
| OFF\_HEAP（实验）                         | 与 `MEMORY_ONLY_SER` 类似，但把数据放在堆外内存中。这需要显式启用堆外内存配置，通常是为了进一步控制 GC 开销。             |

表格 11‑2 存储级别

`OFF_HEAP` 的主要价值，是把部分缓存数据移出 JVM 堆，从而缓解垃圾回收压力。但它也会带来更复杂的运维与容量规划要求，因此并不是大多数任务的默认选择。对多数应用来说，先在 `MEMORY_ONLY`、`MEMORY_AND_DISK`、序列化缓存和是否真正值得缓存之间做好取舍，往往比一开始就上堆外内存更重要。
